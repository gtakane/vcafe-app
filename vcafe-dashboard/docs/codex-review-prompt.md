# Codex へのレビュー依頼プロンプト

以下をそのまま Codex に貼り付けて使う。リポジトリを読ませられる環境（Codex CLI / IDE 拡張）で実行することを想定している。

---

## 貼り付け用プロンプト

あなたはシニアのフルスタックエンジニア兼データエンジニアとして、稼働中の社内向け分析ダッシュボードをレビューしてください。忖度は不要です。**「良い点の列挙」は各セクション最大2行に留め、残りは全て問題点と改善提案に充ててください。**

### 対象

リポジトリ `gtakane/vcafe-app`、ブランチ `claude/nextjs-firebase-dashboard-review-w74yfo`、ディレクトリ `vcafe-dashboard/`。

### プロダクトの背景

「Virtual あっとホームカフェ」というオンライン接客サービスの、**運営社内向け**分析ダッシュボード。閲覧者は運営管理者（admin）とメイド本人（maid）の2ロール。メイドは自分の実績しか見られない。

ドメインの要点:

- **ご帰宅** = ユーザーがメイドの部屋に入室して接客を受けること（1回の来店）
- 座席モデル: 1人のメイドに**同時最大3名**が着席。**1枠20分**。よってメイド1時間の稼働 = 最大9名分
- **営業日は19:00〜翌2:00**。JST 0:00〜1:59 に発生した記録は**前日の営業日**として集計する
- 通貨は「あっとコイン」。フォールバックの換算レートは 1ac = 1.4円
- サービスは **WEB版からアプリ版へ移行**しており、同じ意味のデータが複数のコレクションに分散している

### アーキテクチャ

```
本番 Firebase (v-athome-cafe-app)     ← 読み取り専用。書き込みは絶対に行わない
  └ Firestore
       ↓  Cloud Run Job (services/analytics-sync) 毎時
分析 GCP (vcafe-admin-analytics)
  ├ BigQuery: *_raw テーブル（追記）+ *_current ビュー（ROW_NUMBER で最新行を採用）
  └ Cloud Run Service: Next.js App Router のダッシュボード
```

- ユーザーIDは同期時に **HMAC-SHA256 で仮名化**して分析側へ渡す（Secret Manager 管理）
- 認証は Firebase Auth のセッションクッキー + カスタムクレーム（`role`, `maidId`）

### 特に見てほしい観点

1. **正確性 / データ整合性**
   - 集計ロジックに二重計上・取りこぼし・境界条件の誤りはないか
   - 営業日（19:00〜翌2:00）の扱いが全経路で一貫しているか
   - `*_current` ビューの重複排除（`ROW_NUMBER() OVER (PARTITION BY id ORDER BY syncedAt DESC)`）が、ストリーミング挿入の順序保証がない前提で正しいか
   - `payments_current` が `source='userPayments'` を正とし、台帳が空のときのみ旧ソースへフォールバックする構造の妥当性

2. **セキュリティ**
   - API ルートのロール検証（admin/maid）に漏れはないか。maid が他人のデータを取得できる経路はないか
   - BigQuery クエリの組み立て（並び替えキーと数値フィルタ列は**ホワイトリスト経由でのみ SQL に埋め込み**、値はパラメータ化）に穴はないか
   - 仮名化の設計は妥当か（HMACの鍵運用、逆引き耐性、分析側に残る準識別子の組み合わせによる再識別リスク）
   - 本番 Firestore への書き込みを防ぐガード（`CONFIRM_READ_ONLY_SYNC` 等）は十分か

3. **パフォーマンス / コスト**
   - `data-source.ts` が期間内の全 visit/shift/customer を `TO_JSON_STRING` で1クエリにまとめて返している設計の限界。データ量が10倍になったときに最初に壊れるのはどこか
   - `maximumBytesBilled` の設定値と、パーティション/クラスタリングの使い方は適切か
   - クライアント側で全件を保持して集計している箇所のメモリ・描画コスト

4. **設計 / 保守性**
   - `dashboard.tsx` 716行の単一クライアントコンポーネントをどう分割すべきか。**具体的な分割案**（ファイル名と責務）を提示してほしい
   - 業務ロジックが `lib/metrics.ts` に集約されている一方、Python 実装 `core.py`（リポジトリルート）と**同じ計算を二重管理**している。この二重管理を解消する現実的な方針
   - 型定義（`lib/types.ts`）とBigQueryスキーマ（`services/analytics-sync/schema.sql`）の整合を、人手のレビュー以外で担保する方法

5. **テスト**
   - 74件のテストがカバーできていない重要な経路はどこか。**優先度順に5つ**挙げてほしい
   - 特に、同期の変換ロジックが本番データの「壊れた形」に耐えられるかの検証方法

6. **運用**
   - 障害時の切り分けに必要な可観測性が足りているか（現状はログの grep 頼み）
   - `services/analytics-sync/` に診断用スクリプトが10本以上ある。これらを恒久的な仕組みに昇華させるとしたら何を作るべきか

### 既知の制約（指摘不要）

- 本番 Firestore は**読み取り専用**。スキーマ変更・データ修正は運営側の別アプリが行うため、こちら側では直せない
- `firebase deploy --only firestore:indexes` は本番の既存インデックスを削除するため使用禁止
- Streamlit 版（`app.py` / `core.py`）は移行元であり、当面は併存する

### 出力してほしい形式

```
## 総評（5行以内）

## 重大な問題（あれば）
- [深刻度: 高/中/低] 問題 → 根拠となるファイル:行 → 具体的な修正案

## 観点別の指摘
（上記1〜6の観点ごとに、同じ形式で）

## 改善ロードマップ

- 次にやるべき3件
- 余力があれば3件
```

各指摘には**必ず `ファイル:行` の根拠**を付けてください。推測で書く場合は「推測」と明記してください。コードを読まずに一般論だけを述べることは避けてください。
